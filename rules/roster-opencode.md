**Writer executor via OpenCode** (agent defined in `~/.config/opencode/agents/`). Modes via the model variant, when the model offers them — in the rest of this document, "writer-fast" = fast mode and "writer (thinking)" = thinking mode; the responsibility table names the exact variant of each row:
- **Fast mode** (non-reasoning variant): the operational default — closed briefs, decided implementation, mechanical refactors, running and fixing validations, checklist reviews, verbose outputs (builds, suites, logs, seeds), code with context >100K.
- **Thinking mode** (reasoning variant): long-context >100K repo/flow reading (entire modules, huge logs in one pass) and scout fallback.
- **The variant is ALWAYS explicit** (`-m "<provider>/<model>#<variant>"`, the variant of the roster row): without it, a model's default behaviour can change between OpenCode versions without notice (in the reference setup the same model went from reasoning in most messages to never reasoning). After an OpenCode upgrade, confirm in the trace that each variant still behaves as its row says. A non-existent variant returns "Variant unavailable".
- **Invocation** via `Bash`: `cd <dir> && {{ launcher.opencode }} --agent <agent> -m "<provider>/<model>#<variant>" "$(cat <brief>.txt)" </dev/null > <digest>.txt 2> <trace>.txt` — the exact commands of this roster are in the launch examples below. **stdout carries ONLY the final answer** (the digest, the only thing the principal reads) and **stderr the activity trace** (only consulted to debug a failed executor). **NEVER `2>&1`**: it would mix the trace into the digest. Both files go to the scratchpad. Verify in the trace the line `> <agent> · <model>` with the values of the roster row.
- **`-m` is MANDATORY:** OpenCode v2 ignores the agent's `model:` and falls back silently to another model. If in doubt, verify the real model (trace or `opencode.db`).
- **Web search:** verify that the research vehicle really searched (sources and search calls in the trace). A vehicle that returns invented results and reports them as valid is dropped for good. OpenCode's built-in web search performs real searches.
- The writer-executor agent carries a copy of the executor profile (master: `podium/executors/profile/`, rendered by `podium install`; re-render it when it changes) and blocks skills, the memory MCP, other MCPs (except `codegraph`), subagents and `git *` (the global `AGENTS.md` would otherwise force the memory flow on every run).
- OpenCode runs as a background service: a new or edited agent in `~/.config/opencode/agents/` may not be visible until the service restarts.

**Consultant and overflow executor via OpenCode** (consultant = judgement, overflow = mechanical code). Each with its own agent, model and fixed effort — no internal backup among engines of the same family: if the quota drops, the cascade falls through to the engine indicated in the table. Three uses:
- **Consultant `high`** — diagnosis (non-obvious bugs, root cause), review with judgement and second opinion. Read-only, output = short analysis. If diagnosis and second opinion target the same problem, they go in a single consultation.
- **Consultant `xhigh`** — verdict on high-risk architecture/plan decisions. Read-only, concrete question, output = verdict and alternatives, no code.
- **Overflow executor `high`** — mechanical code overflow: when a phase launches many executors in parallel, the 2–3 most mechanical briefs (renames, imports, fixing type/lint errors following a given pattern) go to the overflow executor so the writer executor's quota is not burned all at once. In normal tasks (1–3 agents) all closed-brief code goes to the writer executor. The overflow executor writes mechanical code only, never diagnosis.
- **Invocation** via `Bash` (ALWAYS with agent, `-m` and effort variant explicit): consultant → `cd <dir> && {{ launcher.opencode }} --agent <consultant> -m "<provider>/<model>#<high|xhigh>" "$(cat <brief>.txt)" </dev/null > <digest>.txt 2> <trace>.txt`; overflow executor → `cd <dir> && {{ launcher.opencode }} --agent <overflow> -m "<provider>/<model>#high" "$(cat <brief>.txt)" </dev/null > <digest>.txt 2> <trace>.txt`. Same stdout/stderr rule as the writer executor (NEVER `2>&1`).
- **Agents** (`~/.config/opencode/agents/<consultant>.md` and `<overflow>.md`, with the same executor profile as the writer): the consultant is **read-only enforced by permissions** (no editing, shell limited to `ls`/`cat`/`grep`/`rg`/`find`/`head`/`tail`/`wc`/`sed -n`, no `git`, no subagents); the overflow executor edits, no `git`.

**Conflict between harness mode and cascade: ask, do not assume.** When a system mode suggests native subagents (e.g. Plan mode: "use Explore/Plan") and the cascade indicates an OpenCode executor, the principal does NOT decide alone: asks the user (AskUserQuestion) which channel to use — (a) the harness's official routing (native Explore/Plan, Anthropic quota) or (b) the external-engine cascade (writer executor / consultant via OpenCode per the table). The answer stands for the rest of that task unless the user says otherwise; it is not re-asked on every delegation. If the user chooses the cascade while in Plan mode, every brief is marked read-only — "Do NOT edit or create any files; investigate and report only" — to preserve the mode's guarantee (nothing is modified while planning). The mode's own tools (EnterPlanMode/ExitPlanMode, AskUserQuestion) are used normally: they are harness mechanics, not executors.

- **The brief is ALWAYS written with the agent's file-writing tool (Write), never via shell.** Every brief is written to a scratchpad file and injected with `"$(cat <brief>.txt)"` — `$(...)` output is not re-parsed by the shell, so backticks and metacharacters (for example `` `any` `` or `new Date()`) stay literal and are not executed. Briefs are NEVER inline, not even when they are short or simple: inline briefs pass through the shell, and shell inline interprets backticks and metacharacters as commands. The scratchpad file is the auditable artefact of the brief, and it is reused **unchanged** on fallback so the next executor sees the same instructions.
- **NEVER `&` inside the command:** parallelism is given exclusively by `run_in_background: true` of the Bash tool. Combining both duplicates the backgrounding: the harness tracks a launcher that dies instantly and the real process becomes an orphan, without follow-up or termination notification.
